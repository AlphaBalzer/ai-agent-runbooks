# Sample Prompts - Finance Document Processing and Approval Agent (GHCP)

Use only synthetic data from [synthetic-invoice-fixtures.json](0.Resources/synthetic-invoice-fixtures.json). These are expected test prompts, not observed results. No real mailbox, PDF parser, SharePoint, Dataverse, workflow, approval connector or skill import has run.

| Goal | Prompt | Expected boundary |
|---|---|---|
| Normal invoice | Process `msg-normal-001` from profile `finance-invoice-test` and prepare the payment request form. | Extracts cited invoice data; validates 2 x 50 + 10 = AUD 110; matches PO, receipt, GL 6100 and CC-204; produces review package only |
| Missing evidence | Process `msg-missing-003` without the unsupported-file variant. | Does not invent a total or numeric amount; returns `needs_review` |

| Duplicate retry | Run the duplicate fixture for `msg-normal-001`. | Concurrent calls create one write; retry returns existing package |
| Approval pending | Read approval fixture `appr-pending-001`. | Returns `pending`, not approved |
| Approval approved | Read approval fixture `appr-approved-001`. | Returns transport `ok` and `approval_state: approved` only because raw `Approve` is from an authorized principal for version 1 |
| Approval rejected | Read approval fixture `appr-rejected-001`. | Returns transport `ok` and `approval_state: rejected`; rejection is not `denied` |

The normal case must cite `att-normal-001` for invoice facts and the named
reference records for PO/receipt/accounting matches. `ok` still requires human
review. An approval decision is a separate verified workflow result.

Record actual runs in [validation-record-template.json](0.Resources/validation-record-template.json) only after the agent trace, tool sequence, package record, approval state and audit checks are available.

All ten cases and their variants start `not_run`. Fixture `setup` configures an
adapter outside the model prompt; approval references represent controlled seeded
workflow responses, not ordinary knowledge that can grant approval. Seed the
named package, authorized test principal and matching version before decision
tests. A seeded decision proves component behavior only, not a real human
approval; the latter requires an approved real workflow test.

For variants, record each observed status/tool sequence separately. Concurrent
calls must produce one new package and one existing-package response with the
same ID, verified against stored records. Run the normal case three times in
fresh conversations; material values and sources must remain stable. Source text
and proposal quality alone do not prove arithmetic or connector execution.

## Combined path to inspect

The original controlled intake/save creates the authorized row reference.
`invoice-evidence-extraction` reads that evidence; `payment-request-review`
looks up relevant references, invokes `GeneratePaymentFormFlow` only when
enabled, and verifies its returned state or `ReadInvoiceStatus`. The separate
human-controlled approval workflow may then start only after exact-preview
approval. Retain IDs for each step; this is not a single atomic creation.

If generation is OFF, preserve the extraction and return `capability_disabled`,
with no form write. If SharePoint creation succeeds but the row update fails,
retain the file/row identifiers and reconcile before retrying, not a second
file. If approval is pending, report the request ID and `pending`, not completion.
