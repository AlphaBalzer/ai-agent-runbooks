# Step-by-Step Guide - Autonomous Invoice Orchestration Agent (GHCP)

> **Scenario**: Invoice Processing and Approval<br>
> **Platform**: Microsoft Copilot Studio with GitHub Copilot harness, Power Automate, Outlook, SharePoint and Dataverse<br>
> **Target Readers**: Delivery engineer

## Overview

This agent helps users turn an emailed supplier invoice into a payment request for human
approval. The delivery follows the [standard runbook](../Autonomous-Invoice-Orchestration-Agent/3.Runbook.md):
create the agent, configure intake/save, extract invoice details, generate the form and connect
manager approval.

The GHCP changes are focused on the agent's instructions, reusable skills and approved-source
investigation. Keep the existing storage and approval process. See
[supplied resources and delivery status](0.Resources/README.md#delivery-status) before planning
a live demonstration; the complete Invoice agent-to-approval path is not yet demonstrated.

## Prerequisites

### Core Environment Requirements

| Requirement | Description |
|---|---|
| Copilot Studio environment | An approved test environment with the GitHub Copilot harness and an allowed model. |
| Invoice mailbox | A dedicated test mailbox and agreed synthetic email/attachment content. |
| SharePoint | Fixed locations for source invoices and generated review forms. |
| Dataverse | A transaction/review table with the agreed fields, state and duplicate controls. |
| Finance references | Approved vendor, PO, receipt, GL, cost-centre and no-PO rules as applicable. |
| Human approval | A named authorized approver, reviewed form layout and agreed notification recipients. |

### License Requirements

Confirm Copilot Studio authoring access, approved Copilot Credits or billing, and licenses for
the connectors, Dataverse and intended user channel. Building and testing can consume capacity.
Do not copy unrelated ERP, telemetry or Application Insights prerequisites into this invoice path.

### Access and Permissions

Use scoped mailbox, library and table permissions. Agree read, create/update and notification
permissions separately; read access does not authorize sending. Use synthetic invoices first.
The supplied [storage setup](0.Resources/README.md#storage-setup) describes the bounded test
table and libraries, not a provisioned environment.

## Step-by-Step Instructions

### 1. Create the GHCP agent

1. Open Copilot Studio in the approved environment and solution.
2. Create a blank agent using the **GitHub Copilot harness** and an approved model.
3. Define the job: read the selected invoice, extract cited facts, check approved references
   and prepare a review form or exception. Do not approve, post or pay.
4. For the supplied snapshot-based test configuration, use the unchanged
   [agent instructions](0.Resources/Pilot-agent-instructions.txt). Its fixed tool bindings
   and fictional references must match the configured workflows.
5. Under **Build > Skills > Upload a skill**, add
   [invoice-evidence-extraction](Skills/invoice-evidence-extraction/SKILL.md) and
   [payment-request-review](Skills/payment-request-review/SKILL.md).

Use Microsoft authentication. Keep web search, memory, other-agent access and external channels
off for the supplied test configuration. Uploading skills does not create the tools below.

## Configuring Your Power Automate Flows

Configure the same five business stages as the original. Existing approved flows can be reused
where compatible. The supplied JSON files are
[reconstruction references](0.Resources/README.md#current-workflow-bindings), not solution imports;
the current implementation combines some stages and does not supply an approval flow.

### 2. Configure invoice intake and saving

1. Choose the fixed mailbox, folder and agreed test filter.
2. Configure intake to use the actual received **Message Id**, not a conversation URL.
3. Claim the intake once, save the original supported attachment to SharePoint and record the
   source URL and snapshot in Dataverse.
4. Return the source row ID for the next stage. Preserve partial IDs and reconcile an uncertain
   save before retrying.

Start with one selected message before enabling automatic arrivals. The
[operator-intake reference](0.Resources/Invoice-intake.definition.json) covers the combined
intake/save component. Its selected-environment Dataverse binding and exact field mapping are
in [workflow setup](0.Resources/README.md#workflow-setup).

### 3. Configure invoice extraction and reference checks

1. Attach the scoped source reader and approved finance-reference lookup.
2. Pass the saved source row ID to the agent. Extract vendor, invoice number, dates, line items,
   subtotal, tax, total, currency and any PO reference with supporting quotes.
3. Check the relevant approved records, including supplied GL and cost-centre values.
   Flag missing or conflicting facts instead of choosing a convenient value.
4. Return structured evidence for the form workflow. An extraction result is not financial
   validation or approval.

The supplied `ReadInvoiceMessage` reads a saved snapshot, not the mailbox again. Its attachment
text is already in that snapshot; PDF/OCR support must not be inferred.
[Current bindings and output fields](0.Resources/README.md#current-workflow-bindings).

### 4. Configure payment request form generation

1. Bind `GeneratePaymentFormFlow` to the intended source record and its current version.
2. Have the workflow independently read the source and enforce amounts, reference checks,
   duplicate protection and version checks before creating the form.
3. Use the agreed template, save the form to SharePoint and update its Dataverse state.
4. Return and inspect the actual form URL, record/version and business status.

The supplied component produces a **review JSON file**, not the original's HTML payment form.
Implement and demonstrate the agreed HTML template if required; escape source text and do not
execute model-generated scripts. Missing evidence or a failed check must not become a form
marked ready for approval.

### 5. Configure manager approval and notifications

1. Resolve the approver using the agreed financial authority rules. A directory manager lookup
   alone is not sufficient authorization.
2. Preview the exact form, recipients and notification content before enabling the test flow.
3. Submit through the separate approval workflow and retain its request ID.
4. Record the authorized person's actual `Approve` or `Reject` for the reviewed version.
   Notify the agreed recipients only through that controlled workflow.

Until the decision arrives, the request is pending. Changes to material invoice details require
fresh review. No result authorizes ERP posting or payment. Approval is **not implemented or
enabled in the supplied test configuration**; see [approval controls](0.Resources/README.md#approval-controls).

## Channels

The intended autonomous entry point is invoice email arrival. A selected-record conversation
can also be used to review an existing request.

Before enabling automatic intake, demonstrate selected-record reading and form generation
through the actual GHCP agent. Then configure the supported invocation of the published agent
from intake, pass the source row ID and demonstrate one new email through the complete path.
Do not assume a trigger or publication resolves the recorded Preview issue.

Use the [sample prompts](4.Sample-prompts.md) to inspect source quotes, validation findings,
persisted form/state and the actual human decision. Include duplicate, missing-data, rejected,
changed-source and failure cases. Record what ran and what remains incomplete.

For training today, use the [recorded component walkthrough](0.Resources/README.md#trainer-walkthrough),
not an unrehearsed live end-to-end claim. Remove temporary build privileges after the work and
retain only the approved operating access.
