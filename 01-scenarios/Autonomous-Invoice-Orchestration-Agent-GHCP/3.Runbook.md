# Step-by-Step Guide - Autonomous Invoice Orchestration Agent (GHCP)

> **Scenario**: Invoice Processing and Approval<br>
> **Platform**: Copilot Studio, Power Automate, Outlook, SharePoint and Dataverse<br>
> **Target Readers**: Delivery engineer

## Overview

**PDF arrives -> save it -> extract invoice details -> create the payment request -> manager
approves -> record the outcome and notify.**

This is the same process as the [original runbook](../Autonomous-Invoice-Orchestration-Agent/3.Runbook.md).
The small GHCP addition is an agent with one invoice-review skill: check the extracted information,
consult the agreed accounting reference when needed, and explain anything missing or conflicting.
It does not replace the document-extraction, form or approval workflows.

**Implementation status:** this is the simplified build target, not a finished PDF solution.
The existing text-based test build is preserved separately in
[Resources](0.Resources/README.md#delivery-status). Its successes do not prove this PDF path.
The original supplies instructions and screenshots, not an assumed ready-to-import solution.

## Prerequisites

### Core Environment Requirements

- An approved Copilot Studio environment with GHCP available.
- A test mailbox, SharePoint document library and Dataverse invoice table.
- A digital PDF invoice, such as the original [sample PDF](../Autonomous-Invoice-Orchestration-Agent/0.Resources/Sample_Invoice.pdf).
- The agreed GL/cost-centre reference and an authorized manager for approval.

### License Requirements

Confirm Copilot Studio capacity and the licensing needed for the existing document prompt,
connectors and Dataverse. Do not add an ERP, Azure service or custom server just for GHCP.

### Access and Permissions

Use the approved mailbox, library and table connections. Keep sending/approval authority with
the existing workflows. Begin with synthetic data; scanned or handwritten PDFs need separate
extraction coverage.

## Step-by-Step Instructions

### 1. Create the GHCP agent

1. Open Copilot Studio in the approved environment and solution.
2. Create an agent using the **GitHub Copilot harness**. Do not convert or overwrite the
   original agent.
3. Use the short instruction block below. Configure the original supporting flows in the next
   section, then attach the compatible tools with their actual input/output names.
4. Add one skill under **Build > Skills > Upload a skill**, using the draft below.

**Agent instructions - proposed for the simplified build:**

```text
You coordinate supplier invoice processing.
Use the RowId supplied by invoice intake; do not search for a different invoice.
Call ParseInvoiceFlow and inspect its returned invoice details and status.
Use the invoice-review skill before requesting the payment form.
If facts are missing or conflicting, explain the issue and stop for human review.
When the extraction and required workflow checks succeed, call GeneratePaymentFormFlow
with the same transaction reference and inspect the actual saved form result.
Hand the eligible request to the separately enabled ApprovalRequestFlow.
Report pending until an authorized person's actual decision is recorded.
Never invent tool results, approve an invoice yourself, post or pay.
Preserve existing permissions, duplicate protection and failure handling.
```

**One small skill - draft, not yet imported or runtime-validated:**

```markdown
---
name: invoice-review
description: "Check extracted invoice information before preparing a payment request."
---

# Invoice review

Use the invoice details and source references returned by ParseInvoiceFlow.
Check that the supplier, invoice number, dates, amounts and required accounting
details are present and consistent.
Use the agreed GL/cost-centre reference where needed; do not invent a code.
If the reference is unavailable, or facts disagree, explain what needs review.
Preserve source references exactly. Do not invent quotations or page numbers.
Return a short review summary and unresolved questions to the orchestrator.
Workflow checks, not this skill, determine arithmetic and write eligibility.
This skill does not create files, request approval or authorize payment.
```

![Upload a Markdown skill in the GHCP Build screen](0.Resources/Images/02-upload-skill.png)

**Expected:** one clearly named review skill. The previously supplied two snapshot-based skills
belong to the older test implementation; they are not drop-in replacements for this draft.

## Configuring Your Power Automate Flows

### 2. Receive and save the PDF

Follow the original's **invoice intake** and **save invoice** flows.

1. Scope the email trigger to the agreed test mailbox.
2. Save the original PDF attachment to SharePoint without converting it to a text fixture.
3. Create the invoice transaction in Dataverse and store its file reference.
4. Pass the resulting **RowId** to the GHCP agent through the supported workflow Agent step.

Reference screens: [intake](../Autonomous-Invoice-Orchestration-Agent/0.Resources/image-7.png)
and [save invoice](../Autonomous-Invoice-Orchestration-Agent/0.Resources/image-2.png).

**Expected:** the original PDF in SharePoint and a linked transaction. An end user should not
have to copy a Message Id or edit a per-invoice allow-list. Workflow permissions and duplicate
controls still apply; do not remove the older test build's protections to simulate this behavior.

### 3. Extract the invoice

Keep the original **ParseInvoiceFlow** sequence:

**Get row by ID -> get file content using path -> run the document-extraction prompt -> parse
the returned JSON -> save extracted invoice details.**

Bind the PDF **file content** to a document-capable prompt input, not to a plain-text field.
Use the original extraction prompt/schema as the starting point: JSON only, invoice values
and line items, with missing values explicit. Keep the agreed accounting-reference lookup in
this stage; a separate reference service is not required.

Reference screens: [document extraction](../Autonomous-Invoice-Orchestration-Agent/0.Resources/image-3.png)
and [continued flow](../Autonomous-Invoice-Orchestration-Agent/0.Resources/image-4.png).

**Expected:** invoice details from the PDF, linked to that source. Confirm the selected prompt
and its file-input binding actually work in the target environment. GHCP conversation-upload
support alone is not proof that an emailed PDF reaches this workflow.

**GHCP difference:** after extraction, the agent uses the review skill to flag gaps or conflicting
facts before requesting the form. Keep this review short; do not build another parsing engine.

### 4. Create the payment request form

Follow the original **GeneratePaymentFormFlow**: take the saved invoice details, run its
HTML-form prompt and save the returned form in SharePoint.

Use the original prompt as the starting point, with the agreed layout and invoice values.
Render values as text, escape source content and omit executable scripts or payment controls.
Keep existing financial validation and duplicate handling in the workflow.

Reference screen: [form creation](../Autonomous-Invoice-Orchestration-Agent/0.Resources/image-5.png).

**Expected:** a readable payment request with the correct invoice information and a saved link.
The custom template developed for the earlier text pilot remains available, but is **not an
additional required build step** for this original-first path.

### 5. Obtain manager approval

Keep the original **ApprovalRequestFlow** and notification sequence.

1. Identify the authorized approver. A directory manager lookup alone does not establish
   financial authority.
2. Send the reviewed request through the approved workflow.
3. Record the actual Approve/Reject decision for the reviewed request and notify the agreed
   recipients. Keep human waiting/state tracking in the workflow, not an open model turn.

Reference screens: [approval](../Autonomous-Invoice-Orchestration-Agent/0.Resources/image-6.png),
[notification](../Autonomous-Invoice-Orchestration-Agent/0.Resources/image-9.png) and
[manager mapping](../Autonomous-Invoice-Orchestration-Agent/0.Resources/image-10.png).

**Expected:** a real human decision and recorded outcome. A generated form is not approval;
pending, failed or changed requests must not be treated as approved. Payment execution is excluded.

## Channels

Use the same email-driven entry point as the original. The native workflow
[Agent step](https://learn.microsoft.com/en-us/microsoft-copilot-studio/workflows-experience/agent-node-workflow)
can call a published GHCP agent; configure and demonstrate this with the PDF flow before
claiming end-to-end completion. Publication and sending require the agreed approvals.

For training, prepare the original storage and supporting flows first, then show the small
GHCP change live: agent creation, instructions, one skill and tool connections.
Call this a **prepared-environment build**, not a full blank-screen deployment.

The finish line is one PDF email through extraction, form creation, real manager approval and
the recorded notification. Demonstrate missing-information and rejected cases without expanding
the exercise into an unrelated platform project.
