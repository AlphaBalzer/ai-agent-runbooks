# Step-by-Step Guide - Email & Shared Mailbox Triage Agent (GHCP)

> **Platform**: Copilot Studio with GitHub Copilot harness, Power Automate, Exchange Online<br>
> **Target Readers**: Delivery engineer<br>
> **Planning baseline**: The standard scenario uses 4-6 weeks; allow for source, invocation and downstream integration work.<br>
> **Supplied components and evidence**: [Resources](0.Resources/README.md#delivery-status)

---

## Prerequisites

| Requirement | Owner |
|---|---|
| Approved test environment, maker permissions, DLP/region review and capped capacity | Platform team |
| Dedicated test shared mailbox and authorized connection identity | Mailbox administrator |
| Permitted sample messages and approved reference material | Mailbox team |
| Supported GHCP invocation path for the intended intake mode | Delivery engineer |
| Chosen downstream action, connection and approval rules | Business owner / platform team |
| Exception owner, retention policy and recovery procedure | Business owner / compliance |

Choose one action variant, not every capability at once. The phases below cover the full delivery
lifecycle. The supplied build references implement assessment and response preparation;
[delivery status](0.Resources/README.md#delivery-status) separates those assets from integration work.

---

## Phase 0 - Discover the Real Categories (Week 1)

### Step 0-1. Sample and label

1. Obtain permission to use representative mailbox history.
2. Label a working sample, using the standard scenario's 300-message baseline where practical.
3. Record intent, urgency, requester, relevant reference, destination and the action actually needed.
4. Reserve separate messages for evaluation. Do not use customer content in a public training package.

### Step 0-2. Build the category set

| Category | Definition | Approved source | Routes to | Action / review gate |
|---|---|---|---|---|
| Policy/process question | Asks how to start or complete a process | Current process guidance | Process owner | Supported draft, human review |
| Status enquiry | Asks about an existing request | Authorized status record | Request owner | Status proposal, human review |
| Document copy request | Asks for a named document | Exact document and entitlement | Document owner | Approved delivery workflow |
| Unclear | Conflict, missing material evidence or multiple intents | Available evidence only | Exception owner | Human triage |

These are starter definitions. Agree the customer's categories before changing the supplied
instructions, skills, output consumers and expected tests together.

### Step 0-3. Baseline the manual process

| Measure | Baseline |
|---|---|
| Messages per year | Record actual volume |
| Minutes per message | Include reading, lookup and drafting |
| Misroute rate | Sample with the mailbox team |
| Time to first response | Measure, do not estimate from model speed |
| Exception backlog | Record age and owner |

**Exit criteria:** categories and approved sources agreed, sample labelled, baseline captured
and exception owner named.

## Phase 1 - Pre-processing (Week 2)

### Step 1-1. Establish the intake path

1. Configure the shared-mailbox arrival trigger in the approved workflow environment.
2. Preserve the actual received message ID and stable duplicate key.
3. Filter auto-replies, bounces and agreed non-actionable mail before agent processing.
4. Confirm the supported method for invoking the GHCP agent and returning its structured result,
   including which identity is used. Demonstrate that connection in the target environment.

**Compatibility gate:** the documented agent-call workflow tool runs in the other direction:
agent to workflow. It does not establish workflow to GHCP agent invocation. Do not substitute
a standard-harness API or browser automation and call it supported unattended operation.
If this connection is unavailable, stop the automatic-intake rollout and record the blocker.
Selected-message Preview remains a supervised exercise, not a substitute for arrival automation.

### Step 1-2. Prepare the message

| Step | Required behavior |
|---|---|
| Newest request | Separate it from earlier quoted history. |
| Signatures and disclaimers | Exclude from classification context where safe; retain original evidence. |
| Forwards | Distinguish sender from requester without inferring authorization. |
| Attachments | Ignore inline logos; declare supported formats and preserve source IDs. |
| Language | Preserve exact identifiers and evaluate each required language. |

**Exit criteria:** usable content and source identifiers reach the agent through the agreed
intake path. A successful mailbox trigger alone is not enough.

## Phase 2 - Downstream Write (Week 2, in parallel)

Build the one agreed action workflow independently of the agent.

| Question | Required decision |
|---|---|
| Target and operation | Exact destination, record type and supported connector action |
| Payload | Allowed fields, attachment handling and destination allowlist |
| Approval | Who approves which action and how that approval binds to the payload |
| Duplicate prevention | Stable mailbox/message/action key with an atomic claim before the effect |
| Failure | Failed, pending and unknown outcomes, readback and bounded recovery |
| Audit | Actual action ID, result and reviewer without unnecessary source content |

1. Exercise the workflow with approved synthetic input and no model.
2. Confirm the expected action and read back its actual result.
3. Replay the same input and confirm no second effect.
4. Exercise rejection, concurrent duplication and timeout/readback behavior.
5. Leave the action disabled until its gate is approved. The supplied two skills do not call
   business-write tools; use the controlled downstream workflow rather than broadening them.

**Exit criteria:** the action works independently, duplicates are controlled and failure
recovery is visible. A model's statement that it created a record is not evidence.

## Phase 3 - Build the Agent (Week 3)

### Step 3-1. Create and configure

1. Create a separate agent with the **GitHub Copilot harness** in the approved test solution.
2. Set its name to **Email & Shared Mailbox Triage Agent (GHCP)**.
3. Open [Agent instructions](0.Resources/Agent-instructions.md). Copy only the fenced instruction
   block into **Build > Instructions**. The retained name inside that block identifies its recorded
   revision; it does not change the business scenario.
4. Under **Build > Skills > Upload a skill**, upload
   [shared-mailbox-intake](Skills/shared-mailbox-intake/SKILL.md) and
   [grounded-reply-drafting](Skills/grounded-reply-drafting/SKILL.md).
5. Use Microsoft authentication. Keep memory, web search, external channels and extra tools off
   for the controlled exercise. Record the selected model.

The supplied instructions use a fixed fictional reference catalogue and a review-only output
contract. Adapt sources and any required urgency/domain fields together with skills, output
validation and tests before customer deployment. Do not silently assume fields absent from the
supplied JSON contract exist.

### Step 3-2. Add the read and reference tools

Build the two workflows in [Resource setup](0.Resources/README.md#workflow-setup):

| Agent tool | What to attach |
|---|---|
| `ReadSharedMailboxMessage` | Agent-call workflow with fixed mailbox, message-ID input and explicit read/attachment statuses |
| `LookupApprovedReference` | Agent-call workflow returning the approved source text, identifier, version and status |

Use **Build > Tools > Add > Workflow**. Create the trigger, connector/data steps and response
nodes, then save and publish the **workflow** after approval. Attaching a workflow does not
require publishing the agent to users. Reload the saved agent and inspect both tool mappings.

Do not leave an unrestricted mailbox connector as an alternate path around the fixed-mailbox
workflow. The [JSON files](0.Resources/README.md#included-assets) are field/expression references,
not files to import as a solution.

### Step 3-3. Run one supervised example

1. Open the [sample prompts](4.Sample-prompts.md#connected-preview-walkthrough).
2. Prepare the synthetic normal email and obtain its actual received ID using the steps there.
3. Open the agent's **Preview** tab and start a **New chat**.
4. Copy the connected prompt, replace `<message_id>` with the ID and send it once.
5. Inspect the message read, relevant reference lookup and final review response.
6. Confirm the source quotes and `requires_human_review: true`. Confirm no business write occurred.

This establishes the assessment path, not automatic intake or downstream action execution.

### Step 3-4. Connect the business decision

1. Validate the structured response before a workflow consumes it. Reject missing fields and
   unsupported categories; never convert failed/denied reads into successful decisions.
2. Resolve the approved destination from the business-owned route map, not arbitrary model text.
3. Bind the exact proposed action to the required human gate.
4. Call the independently tested action workflow after authorization and report its actual result.
5. Exercise one complete received-message-to-reviewed-action example using the approved intake path.

**Exit criteria:** configured skills and tools, verified source evidence, and a recorded complete
path for the chosen delivery variant. Review-only results do not pass an action-delivery gate.

## Phase 4 - Evaluate Against Real Mail (Week 4)

### Step 4-1. Hold-out test

Use a permitted, representative hold-out set. The original scenario uses 100 messages and
the targets below as a starting point; agree appropriate targets with the mailbox owner.

| Metric | Starting acceptance target |
|---|---|
| Classification accuracy | At least 85% overall; no category below 70% |
| Unsupported or confident misroutes | Near zero; inspect every consequential error |
| Required field extraction | At least 90%, with no fabricated references |
| Material draft claims | Supported by accessible, exact evidence |
| Forbidden actions | None |
| Duplicate effects | None across agreed replay/concurrency tests |

### Step 4-2. Test the messy cases

Run the [test corpus](4.Sample-prompts.md): long threads, missing sources, conflicting
attachments, unsupported files, malicious instructions and tool failures. Preserve failed
expectations and record corrections separately.

Native **Evaluate** can help assess response quality, but its General quality score is not an
expected-answer comparison or proof of correct business effects. Inspect actual calls, evidence,
backend outcomes and reviewer decisions.

### Step 4-3. Per-language accuracy

Report accuracy and exception rates per supported language. Do not hide weak performance behind
an acceptable aggregate.

**Exit criteria:** agreed case coverage and thresholds met, remaining limitations accepted by the
owner, and no unsupported claims of action, access or source evidence.

## Phase 5 - Pilot in Shadow Mode (Week 5)

Run assessment alongside the human process with business actions disabled. Mail access and
content handling still require permission; shadow mode is not free of privacy risk.

| Day | Messages | Agent agrees with reviewer | Disagreements | Unsupported recommendations |
|---|---|---|---|---|
| Record daily | Count | Count / rate | Review each | Explain each |

Compare classifications, sources and draft usefulness. Exercise review queue ownership and
failure recovery, not just the normal answer. Keep source evidence in approved storage.

**Exit criteria:** stable quality, no unhandled consequential errors, owned exceptions and an
agreed action-enablement decision.

---

## Phase 6 - Go Live and Operate

1. Confirm the complete intake-to-action path and all release decisions are evidenced.
2. Publish only through the approved deployment process.
3. Enable one proven, low-consequence category/action first.
4. Add other actions separately. Keep model-drafted external replies behind human review.
5. Keep a tested disablement and reconciliation procedure for in-flight work.

| Cadence | Activity | Owner |
|---|---|---|
| Daily initially | Exceptions, failures and misroutes | Delivery engineer / queue owner |
| Weekly | Accuracy, reference freshness and queue age | Team leader |
| Monthly | Volume, handling time and capacity against baseline | Business owner |
| On instructions, skills or source changes | Rerun affected cases and release gates | Delivery engineer |
| Continuous | Alert on failures and unexpected zero throughput | Platform team |

## Deliverables Checklist

- [ ] Representative labelled sample, category set and manual baseline
- [ ] Named reference, exception and records owners
- [ ] Supported intake-to-GHCP invocation demonstrated
- [ ] Pre-processing and attachment scope verified
- [ ] Agent, two skills and scoped read/reference tools configured
- [ ] Output contract and business-owned routing gate validated
- [ ] Chosen downstream action demonstrated with approvals, duplicate protection and readback
- [ ] Complete end-to-end case and failure coverage recorded
- [ ] Hold-out and per-language targets met
- [ ] Shadow-mode comparison and release decision completed
- [ ] Handoff, operating owners, alerts and recovery procedure agreed

This is a delivery checklist, not a statement that every item is already supplied or passed.
Read the [current delivery status](0.Resources/README.md#delivery-status) before planning a demonstration.
