# Step-by-Step Guide - Email & Shared Mailbox Triage Agent (GHCP)

> **Platform**: Copilot Studio with GitHub Copilot harness, Power Automate, Exchange Online<br>
> **Target Readers**: Delivery engineer<br>
> **Planning baseline**: 4-6 weeks, dominated by category discovery and downstream integration, as in the standard scenario.

Similar to the standard-harness version, this delivery follows the phases below. The main
change is in Phase 3: configure GHCP skills and approved sources so the agent can investigate
before recommending an action. See [supplied resources and delivery status](0.Resources/README.md#delivery-status).

## Phase 0 - Discover the Real Categories (Week 1)

The routing rules need to be clear before the agent can apply them.

### Step 0-1. Sample and label

1. Obtain approved mailbox history.
2. Take a representative sample of 300 messages, not just clean examples.
3. Have the mailbox team label each: what it was, where it went and which action was needed.

### Step 0-2. Build the category set

| Category | Definition (mutually exclusive) | Volume in sample | Routes to | Action |
|---|---|---|---|---|

Keep a small set of non-overlapping categories and include `Unclear`. Have two people label the
same 20 messages; resolve disagreements in the definitions. Identify the approved sources the
agent can consult, such as intake guidance or request status.

### Step 0-3. Baseline the manual process

| Measure | Today |
|---|---|
| Messages per year | |
| Minutes per message to triage | |
| Misroute rate | |
| Time to first response | |
| Backlog at peak | |

**Exit criteria:** labelled sample, agreed categories and sources, baseline captured and exception owner named.

## Phase 1 - Pre-processing (Week 2)

Build the intake workflow before classification. Keep the original message available as evidence.

| Step | Implementation | Tested |
|---|---|---|
| Trigger on mail arrival | Outlook shared-mailbox trigger, scoped to the agreed mailbox | |
| Filter noise | Auto-replies, bounces and newsletters, before the agent | |
| Separate signatures and disclaimers | Keep boilerplate out of classification | |
| Isolate the newest request | Keep quoted history as context | |
| Detect forwards | Distinguish sender from requester | |
| Handle attachments | Ignore inline logos; extract only supported formats | |
| Detect language | Preserve identifiers and source wording | |

Pass the received message ID to the workflow's **Agent** step configured in Phase 3.
Test the intake on representative mail. [Detailed workflow setup](0.Resources/README.md#workflow-setup).

## Phase 2 - Downstream Write (Week 2, in parallel)

Choose one action first, usually classify-and-route. Reuse the approved action workflow where available.

| Question | Answer |
|---|---|
| Destination and operation | |
| Required fields and attachments | |
| Connection and sending/write permissions | |
| Duplicate-prevention key | |
| Which cases need approval? | |
| What happens after rejection, failure or timeout? | |

Test the action independently with synthetic input before connecting it to the agent.
Confirm the actual result, prevent duplicate effects, and reconcile uncertain outcomes before retrying.
See [action controls](0.Resources/README.md#action-controls) for implementation detail.

## Phase 3 - Build the Agent (Week 3)

1. Create a Copilot Studio agent using the **GitHub Copilot harness** in the approved solution.
2. Configure its role, categories and boundaries using [Agent instructions](0.Resources/Agent-instructions.md).
   Replace the training references with the agreed business sources for customer delivery.
3. Upload the two skills under **Build > Skills**:
   [shared-mailbox-intake](Skills/shared-mailbox-intake/SKILL.md) and
   [grounded-reply-drafting](Skills/grounded-reply-drafting/SKILL.md).
4. Attach the scoped mailbox-read and approved-reference tools. Run the
   [normal Preview example](4.Sample-prompts.md#connected-preview-walkthrough) and inspect the evidence.
5. After the agreed publication approval, publish the agent. In the intake workflow, add an
   **Agent** step, select that published agent and pass the received message ID in its message.
6. Use its structured result to select the approved route or action. Apply the rules below,
   then demonstrate one new email through to its actual downstream outcome.

| Result | Workflow behavior |
|---|---|
| Routine request, sufficient evidence, approved low-risk route | Route automatically when that action is explicitly enabled. |
| Missing information, conflict, sensitive content or failed lookup | Hold for the responsible reviewer; do not guess or bypass the failure. |
| Model-drafted external reply | Require human approval of the content and recipients before sending. |

**Approval is not required for every production email.** The supplied review-only configuration
does require review of every result. Enable automatic routing as a separate, evaluated action
policy; do not simply ignore its review flag.

The agent assesses and prepares. The workflow enforces permissions, approval and execution.
[Field mappings and configuration notes](0.Resources/README.md#connect-the-published-agent).

## Phase 4 - Evaluate Against Real Mail (Week 4)

### Step 4-1. Hold-out test

Use 100 labelled messages the agent has not seen. Agree targets with the mailbox owner; these
starting targets follow the standard scenario.

| Metric | Result | Target |
|---|---|---|
| Overall classification accuracy | | At least 85% |
| Accuracy per category | | No category below 70% |
| Confident or unsupported misroutes | | Near zero |
| Required field extraction | | At least 90%; no invented references |
| Material claims in drafted responses | | Supported by accessible evidence |
| Duplicate or unapproved actions | | None |

Inspect actual tool calls and downstream outcomes, not just the wording of the answer.
Compare handling time and manual reference-checking effort with the existing process.

### Step 4-2. Test the messy cases

Use the [sample cases](4.Sample-prompts.md): long threads, forwards, conflicting attachments,
missing references, unsupported files and tool failures. Complaints and legal correspondence
go to the responsible team, not an automatic generated reply.

### Step 4-3. Per-language accuracy

Report accuracy and exception rates for each supported language. A good overall result can
hide poor handling of a less common language.

---

## Phase 5 - Pilot in Shadow Mode (Week 5)

Run alongside the human process with business actions disabled.

1. The agent records its assessment, evidence and recommendation.
2. People triage as normal.
3. Compare daily and investigate disagreements.

| Day | Messages | Agent agreed with human | Disagreements | Unsupported recommendations |
|---|---|---|---|---|

Move to live when quality is stable, exceptions are owned and consequential errors are resolved.
Existing permissions and retention rules still apply in shadow mode.

---

## Phase 6 - Go Live and Operate

1. Enable one proven, low-consequence category/action first through the approved release process.
2. Add categories as each proves out. Keep uncertain and sensitive cases in human review.
3. Enable replies last: approved templates follow the agreed policy; model-drafted replies require review.

| Cadence | Activity | Owner |
|---|---|---|
| Daily initially | Exceptions and misroutes | Delivery engineer / queue owner |
| Weekly | Category accuracy and reference freshness | Team leader |
| Weekly | Exception queue depth and age | Queue owner |
| Monthly | Volume and response time against baseline | Business owner |
| On category, skill or source changes | Rerun affected cases | Delivery engineer |
| Continuous | Alert on failures and unexpected zero throughput | Platform team |
