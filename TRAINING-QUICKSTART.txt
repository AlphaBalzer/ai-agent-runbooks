21 September 2026 | Review handoff, not release sign-off

THE ONE-SENTENCE EXPLANATION
The agent investigates and explains evidence; workflows enforce fixed actions;
a person retains authority. A review package is not an approval or a payment.

WHAT YOU CAN TEACH NOW
Shared Inbox: a bounded connected demonstration, with recorded normal,
conflicting, malicious, unsupported and controlled-failure cases.
Invoice: working intake and normal review-package workflow components, with
duplicate and source-version safeguards. A corrected connected agent read/
reference review passed, but Preview does not reliably pick up saved tools.
Do not advertise Invoice as a reliable live end-to-end agent demonstration yet.

20-MINUTE SESSION
0-3 minutes: Explain scenario versus skill versus technical pattern.
  Scenario: the business result.
  Skill: reusable reasoning/procedure instructions.
  Pattern: reusable connectors, scoped workflows and storage controls.
3-10 minutes: Shared Inbox.
  Open its Runbook, then the configured unpublished agent's Preview.
  Select the existing approved normal message; paste the sample prompt.
  Show the source read, reference lookup, exact citations and human-review flag.
  Show the recorded conflicting-attachment example.
  Point out that no message is sent, moved, deleted or marked by the agent.
10-17 minutes: Invoice, clearly labelled COMPONENT demonstration.
  Open the existing normal intake run, its saved source and transaction state.
  Open the normal Generate Review Package run and resulting review JSON file.
  Show integer-cent arithmetic, approved fictional references and source version.
  Show the recorded replay: same package, duplicate, no second file.
  Show the recorded wrong-version run: needs_review before the write.
  Explain the known Preview issue rather than repeatedly retrying in class.
17-20 minutes: Explain boundaries and questions.
  All packages require a person. Approval notifications are off. No payments,
  posting, bank changes, production data or hidden generic write tools.

SIMPLE OPERATOR ROUTINE
1. Confirm the approved test identity, environment and existing fixture.
2. Use the supplied prompt or recorded run, not a newly composed test email.
3. Inspect business status and evidence, not just a green workflow badge.
4. Stop on denied, unavailable, failed or unknown_outcome. Reconcile writes
   before retry. A duplicate is the safeguard working, not another success write.

REHEARSAL AND STOP RULE
Rehearse the exact live path before training. Do not spend an audience's time
debugging Preview. If a configured tool is reported unavailable, use the recorded
native run for illustration and call the live path blocked. Never substitute
a model-only answer and describe it as connected execution.
